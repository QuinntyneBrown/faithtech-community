# L2 - Detailed Requirements

Every acceptance test must start with a header naming the L2s it covers, for example `// Traces to: L2-012`.

Viewport names follow the design system breakpoints (`docs/design-system/tokens`): XS <640px, SM >=640px, MD >=768px, LG >=1024px, XL >=1280px.

---

## L2-001: Sign up
**Traces to:** L1-001

Anyone can create an account with a name, email and password on an organisation's community host. The account is global and the profile it creates is a membership of that organisation (`L2-132`). New profiles hold no role.

**Acceptance Criteria:**
1. Given an unused email and a valid password, when the visitor submits the sign-up form on an organisation's host, then the account is created, a profile with no role is created in that organisation (`L2-132` AC1), an email-verification message is sent, and the visitor sees the verify-email page.
2. Given an email already registered, when the visitor submits, then the system shows the same "check your email" outcome without revealing that the email exists; on verification the existing account gains a profile in that organisation if it has none (`L2-132` AC1).
3. Given a password shorter than 12 characters or found in a breached-password list, when the visitor submits, then the form shows an inline error on the password field and no account is created.
4. Given an empty or malformed field, when the visitor submits, then each invalid field shows an inline error, focus moves to the first invalid field, and the error is announced to screen readers.
5. Given the form is submitting, when the request is in flight, then the submit button is disabled and shows a busy state.
6. Given a name longer than 100 characters after trimming, when the visitor submits, then the name field shows "Use 100 characters or fewer for your name." and no account is created, so every new name can be saved unchanged in the profile editor (`L2-006`).

## L2-002: Email verification
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given a valid, unexpired verification link, when the user opens it, then the email is marked verified and the user is taken to set up their profile.
2. Given a verification link older than 24 hours or already used, when the user opens it, then an error page offers to resend the link.
3. Given an unverified account, when the user signs in, then they can browse, but a banner asks them to verify their email and offers a resend, and RSVPing, creating content and sending invites are refused until the email is verified.
4. Given a resend request, when more than 3 resends have been requested in the last hour, then the request is rejected with a "try again later" message.

## L2-003: Sign in and sign out
**Traces to:** L1-001

The Angular app signs in with OAuth2 authorization code + PKCE against OpenIddict. One identity server serves every organisation host (`L2-131`, ADR 0032).

**Acceptance Criteria:**
1. Given a verified account and correct credentials, when the user signs in, then an authorization code is exchanged with PKCE for tokens, and the user lands on the page they first requested, or the home page.
2. Given incorrect credentials, when the user signs in, then a generic "email or password is incorrect" error is shown.
3. Given 5 failed attempts within 15 minutes, when a 6th is made, then the account is locked out for 15 minutes; failed attempts older than 15 minutes, or made before a successful sign-in, a password reset or an elapsed lockout, do not count.
4. Given a membership suspended by a holder of `AdministerOrganisation` (`L2-039`), when the user signs in on that organisation's host, then sign-in is refused with "Your membership of {organisation name} is suspended" (`L2-132` AC5); given an account locked by a platform operator (`L2-148` AC5), when the user signs in on any host, then sign-in is refused with a "your account is suspended" message (`L2-132` AC6).
5. Given a token request without a valid PKCE code verifier, when it reaches the token endpoint, then it is rejected.
6. Given a signed-in user, when they sign out, then their tokens are revoked, and any further API call with those tokens returns 401.
7. Given an expired access token and a valid refresh token, when the app calls the API, then the token is refreshed silently.
8. Given "Keep me signed in on this device" is not ticked, when the browser session ends, then the refresh token is discarded and the user must sign in again.
9. Given a signed-in user on any page and at any width, when they open the account menu from their avatar in the top bar, then it offers "Your profile", "Settings", "Switch organisation" when the account has more than one membership (`L2-133` AC3) and "Sign out", and "Sign out" ends the session on this device as in criterion 6.

## L2-004: Password reset
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given any email, when the user requests a reset, then the same confirmation message is shown whether or not an account exists, and an email is sent only if it does.
2. Given a valid reset link younger than 1 hour, when the user sets a new valid password, then the password is changed, every existing session for that account is revoked, and the user can sign in.
3. Given an expired or already-used reset link, when the user opens it, then an error offers to request a new link.

## L2-005: Profile visibility
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given an anonymous visitor, when they request any profile page or profile API, then they are redirected to sign in (page) or receive 401 (API).
2. Given a signed-in member, when they open another member's profile, then they see the name, featured photo, photos, home {chapter} (`L2-141` AC1) and roles, each role with its {chapter} tag when it has one (`L2-141` AC3).
3. Given a private contact that has not been linked, when any user other than its owner or a holder of `AdministerOrganisation` requests it as a profile, then the response is 404.
4. Given a member's avatar on any screen, when it renders, then its colour is derived from the member's profile id and is the same on every screen (the top bar, the profile, tables); a private contact who has not signed up, and a suspended member (`L2-039`), show the plain avatar.

## L2-006: Edit own profile
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a signed-in user, when they change their name, home {chapter} (a picker of the organisation's active chapters, shown only when chapters are on, `L2-141` AC1) or bio and save, then the profile updates and a success toast is shown.
2. Given an empty name or a name longer than 100 characters, when they save, then an inline error is shown and nothing is saved.
3. Given a user who does not hold `AdministerOrganisation`, when they try to edit another user's profile through the API, then the response is 403.
4. Given a bio longer than 400 characters, when they save, then an inline error is shown.
5. Given the bio field, when the user types, then a counter under it shows how many of the 400 characters are left; once the bio is longer than 400 characters it says how many characters too many, in the danger colour, and nothing is cut off.

## L2-007: Profile photos
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a JPEG, PNG or WebP file of 5 MB or less with alt text, when the user uploads it, then it is resized on the server, stored in blob storage with metadata removed, and shown on the profile within 5 seconds.
2. Given a file larger than 5 MB, of another type, or whose content does not match its extension, when the user uploads it, then it is rejected with an inline error.
3. Given empty alt text, when the user uploads, then the upload is blocked with "Describe this photo".
4. Given a profile with 10 photos, when the user tries to add another, then the upload control is disabled and explains the limit, and the API rejects the upload.
5. Given several photos, when the user marks one as featured, then it becomes the only featured photo.
6. Given the featured photo is deleted after confirmation, when other photos remain, then the most recently uploaded remaining photo becomes featured.
7. Given an uploaded photo, when the owner changes its description to non-empty text and saves, then the new alt text is stored; an empty description is blocked with "Describe this photo".
8. Given blob storage is unavailable, when the user saves a valid photo, then the photo is kept with its description, counts towards the 10-photo limit and the featured rule, is shown as "Saved. It shows on your profile once it finishes storing.", and appears without uploading again once storage recovers; a photo deleted while storage is down is removed at once and its blob is deleted later (`L2-047`).
9. Given two photo writes on one profile that overlap (uploads, featuring or deleting), when both settle, then the profile holds at most 10 photos and exactly one featured photo when it has any, and the write that lost is refused with "Your photos changed while this was saving. Reload and try again." and leaves no photo or blob behind.

## L2-008: Multiple global roles
**Traces to:** L1-003

The roles are the organisation's non-archived role definitions (`L2-136`); each carries a set of capabilities from the platform catalogue (`L2-135`). A profile is a membership of one organisation (`L2-132`), so its roles are held in that organisation.

**Acceptance Criteria:**
1. Given a profile, when roles are assigned, then it can hold any combination of the organisation's roles at once, each assignment optionally tagged with a {chapter} when its definition is chapter-scopable (`L2-141` AC3), and no tag limits what the holder may see (`L2-142`).
2. Given a new profile, when it is created, then it holds no role.
---

## L2-009: Role assignment limits
**Traces to:** L1-003

Who may add or remove which role is defined by the organisation's grant rules (`L2-137`) and applied as `L2-138` and `L2-143` describe; this requirement defers to them. The FaithTech seed (`L2-151`) reproduces the former fixed limits as data: the role seeded as City Lead grants six roles, and only the role seeded as System Admin grants City Lead, Staff and System Admin.

**Acceptance Criteria:**
1. Given a holder of `AssignRoles`, when they add or remove a role that a grant rule lets one of their roles grant, on any profile in the organisation, then the change succeeds and the profile owner is notified (`L2-138` AC1).
2. Given a holder of `AssignRoles`, when they try to grant or remove a role that no grant rule lets them grant, then the option is not shown and the API returns 403 (`L2-138` AC2).
3. Given a holder of `AdministerOrganisation`, when they grant or remove any role, then the change succeeds without a rule and an audit entry is written (`L2-138` AC3, AC5).
4. Given a member without `AssignRoles` or `AdministerOrganisation`, when they try to change roles through the API, then the response is 403 (`L2-138` AC4).
5. Given a removal, when the add-role or remove-role dialog is confirmed, then the profile's roles update without a page reload.
6. Given the last active, unsuspended holder of a role carrying `AdministerOrganisation`, when anyone tries to remove that role, then the change is refused (`L2-139` AC1).

## L2-010: Send invites
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a holder of `InviteMembers`, when they send an invite to a valid email with an optional personal note, then an invite email is sent in the organisation's name (`L2-134` AC5) with a single-use link that expires after 14 days.
2. Given a pre-assigned role, when the inviter chooses one, then only the roles the inviter's grant rules allow (`grantableRoleIds`, `L2-137` AC5) can be chosen, and the API refuses any other role with 403.
3. Given a member without `InviteMembers`, when they call the invite API, then the response is 403.
4. Given the invites page, when a holder of `InviteMembers` views it, then it lists the invites sent by every member of the organisation who holds `InviteMembers`, each with its status: pending, accepted or expired.
5. Given an expired invite, when a holder of `InviteMembers` chooses "Resend", then a new invite with a new 14-day link is sent.
6. Given more than 50 invites from one user in 24 hours, when another is sent, then it is rejected with a rate-limit message.
7. Given more than 50 invites, when a holder of `InviteMembers` opens the invites page, then it shows the newest 50 with "Showing 50 of N invites", and "Show more invites" loads the next 50 (pages hold at most 100, `L2-046`) without repeating or skipping any invite, even when invites are sent meanwhile; when loading more fails, the invites already shown stay and "We couldn’t load more invites. Try again." is shown.

## L2-011: Accept invites
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a valid invite link, when the invitee signs up with the invited email, then the email counts as verified, a profile is created in the inviter's organisation whatever host the invitee started on (`L2-132` AC2), and any pre-assigned role is granted to that profile.
2. Given an expired, revoked or used invite, when the invitee opens it, then they see an error and a link to normal sign-up on the organisation's host.
3. Given an existing account, when its owner accepts an invite, then a profile is created in the inviter's organisation if the account has none there, and the pre-assigned role is added to that profile.
4. Given an invite is accepted, when the acceptance completes, then the inviter receives an in-app notification.
5. Given a new account, when the invitee enters a name longer than 100 characters after trimming, then the name field shows "Use 100 characters or fewer for your name." and no account is created (`L2-006`).

## L2-013: Create, edit and search contacts
**Traces to:** L1-005

**Acceptance Criteria:**

## L2-017: Partner records
**Traces to:** L1-006

Partners are read by holders of `ViewPartners` and written by holders of `ManagePartners` (`L2-135`). A holder of `AdministerOrganisation` may do either without the capability, audited as an override (`L2-135` AC5).

**Acceptance Criteria:**
1. Given a holder of `ManagePartners`, when they add a partner with a name, an optional website, offering, owner (a member holding `ManagePartners`), contact details and notes, and a stage (the organisation's initial stage by default, `L2-144` AC3; seeded as Lead, In Funnel and Confirmed in FaithTech, `L2-151`), then the partner appears in that stage.
2. Given a partner, when any holder of `ViewPartners` views it, then every holder sees the same record (one shared pipeline across the organisation).
3. Given a holder of `ViewPartners` without `ManagePartners`, when they view partners, then they cannot create, edit or move partners, and the API returns 403 for writes.
4. Given a member without `ViewPartners`, when they request partners, then the response is 403.

## L2-026: Global search
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given a signed-in member, when they search, then results are grouped into people, events, partners, contacts, work items and resources, using Postgres full-text search, and include only the current organisation's records (`L2-130` AC2).
2. Given any user, when results are built, then they include only items that user is permitted to open: their own contacts only (`KeepContacts`), partners only for holders of `ViewPartners`, work items only for workspace members and holders of `ReadAllWorkspaces`, and resources only those the user may open under `L2-060`, never archived ones; a holder of `AdministerOrganisation` holds every capability (`L2-135` AC3).
3. Given no matches, when the search completes, then an empty state suggests other terms.
4. Given a search term shorter than 2 characters, when it is submitted, then no search runs and a hint is shown.
5. Given 100,000 indexed records, when a member searches, then results return in under 500 ms at p95.

## L2-027: In-app notifications
**Traces to:** L1-010

A notification belongs to the organisation it was raised in; on a host a member sees only that organisation's notifications (`L2-130` AC2, `L2-132` AC4).

**Acceptance Criteria:**
1. Given a new notification in the current organisation, when the user is signed in on its host, then the bell shows an unread count, and the panel lists notifications newest first.
2. Given the panel, when the user opens a notification, then it is marked read and they are taken to the related item.
3. Given unread notifications, when the user chooses "Mark all as read", then the count clears.
4. Given the notifications page, when there are none, then an empty state is shown.
5. Given the notifications page, when the user chooses "Unread", then only unread notifications are listed, and "All" lists every notification again.
6. Given more than 50 notifications, when the page loads, then the newest 50 are listed with "Show older notifications", which appends the next 50 and disappears when none are left.

## L2-028: Email notifications
**Traces to:** L1-010

These emails are sent: a contact signed up, an event cancelled or changed, invites, RSVP confirmations, role changes, Agile assignments and workspace additions, Planning Poker invitations, announcements, a resource shared with you and a resource handed to you (`L2-061`, `L2-064`). Only announcement emails can be turned off. Every email is sent on behalf of the organisation it was raised in (`L2-130` AC6, `L2-134` AC5).

**Acceptance Criteria:**
1. Given a triggering action, when it completes, then the email is queued and sent within 2 minutes, retrying on failure for up to 5 delivery attempts in all, counting the first send, after which it is marked failed and not retried.
2. Given an email, when it is rendered, then it includes a plain-text part, every link uses HTTPS and points at the organisation's host, and its sender display name, subject prefix and footer carry the organisation's name (`L2-130` AC6, `L2-134` AC5).
3. Given a user who opted out of announcement emails, when an announcement is sent, then no announcement email reaches them, but other notification emails still do.

## L2-031: Agile workspaces and membership
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given a holder of `OwnWorkspaces`, when they create a workspace with a name and a method (Scrum or Kanban), then they become its owner. A holder of `OwnWorkspaces` can own more than one workspace; a member without it is not offered "New workspace" and the API answers 403.
2. Given the owner, when they add members, then only profiles holding `JoinWorkspaces` can be chosen, and each added member is notified.
3. Given a member, when they open the workspace, then they can create and edit stories and tasks, move cards, comment and vote in Planning Poker. Only the owner creates and edits initiatives and epics.
4. Given a member who is not the owner, when they try to manage members, change settings, manage sprints, or archive the workspace, then the control is hidden and the API returns 403.

## L2-060: Visibility and access on the server
**Traces to:** L1-020

**Acceptance Criteria:**

Given a selection, when the owner presses Ctrl+K or chooses "Link", then the "Add a link" dialog opens with "Link" (hint "Starts with https:// or mailto:") and "Add link"; a link that does not start with `https://` or `mailto:`, is not a valid URL or is longer than 2,000 characters shows "Use a link that starts with https:// or mailto:", and the API answers 400 for a span whose `href` breaks the same rule.

6. Given the caret at the start of a Text block, when the owner types `# `, `## `, `### `, `- ` or `* `, `1. `, `[] `, `> `, ` ``` ` or `---`, then the block turns into Heading 1, Heading 2, Heading 3, Bulleted list, Numbered list, To-do, Quote, Code or a Divider (followed by a new empty Text block) and the typed marker is removed; typed anywhere else, the same characters stay as text.

10. Given a text-bearing block, when the owner chooses "Turn into" in its block menu (`L2-089`), then the block becomes the chosen text-bearing type, keeping its text and inline formatting (a Code block keeps the text only), a To-do starts unchecked, and focus returns to the block.

## L2-089: Reorder blocks by drag and by keyboard
**Traces to:** L1-022

Blocks are ordered by their position in the saved block list; reordering changes that order and is saved by autosave (`L2-086` AC8). Every drag has a keyboard and single-pointer alternative (WCAG 2.2 SC 2.5.7).

**Acceptance Criteria:**
1. Given the editor, when a block renders, then it has a drag handle labelled "Move or open the menu for block {n} of {total}, {type}", visible on focus and hover and always visible on touch screens.
2. Given the owner drags a block by its handle, when they move it over the page, then a drop indicator shows where it will land; when they drop it, then the block moves there and the new order is saved; dropping outside the page or pressing Escape cancels the drag and nothing changes.
3. Given the owner activates a handle by click, Enter or Space, when the block menu opens, then it offers "Turn into" (`L2-088` AC10), "Move up", "Move down", "Duplicate" and "Delete", with "Move up" disabled on the first block and "Move down" disabled on the last; a Callout adds "Change icon" (`L2-087` AC6) and an Image adds "Edit alt text" (`L2-097`).
4. Given focus or the caret in a block, when the owner presses Alt+Shift+↑ or Alt+Shift+↓, or chooses "Move up" or "Move down", then the block moves one position, keeps focus (and the caret position), and the new order is saved; at the first or last position nothing moves.
5. Given a block is moved by any means, when the move completes, then a polite live region announces "Moved {block} to position {n} of {total}", where {block} is the type followed by up to four first words of its text in quotes (for example "Moved Heading 2 “Run sheet” to position 3 of 12").
6. Given the owner chooses "Duplicate", when it completes, then a copy of the block with the same type, text, formatting and state is inserted below it and focused; "Delete" removes the block and moves focus to the previous block, or the next one when it was the first.
7. Given blocks were reordered and saved, when the page is opened again by anyone who may open it, then the blocks are in the saved order.
8. Given the read-only view, when the page renders, then no handle, block menu, drag or move shortcut is available.

## L2-090: Page links and backlinks
**Traces to:** L1-022

A page link is a span with a `pageId`. The server stores page links without their text and fills the text at read time, so a page's title never reaches someone who may not open it. The `NoteLinks` set of a page is rebuilt from its page links on every save and drives "Linked from".

**Acceptance Criteria:**
1. Given the caret in a text-bearing block other than Code, when the owner types `[[`, then the "Link to a page" suggestions open, listing up to 10 non-archived pages the owner may open, excluding the current page (`GET /api/notes/links?q=&exclude={id}`), most recently edited first, each with its icon and title; typing filters them by title, ↑ and ↓ move the active option, Enter or a click inserts a page link, and Escape closes the list leaving the typed text; with no match it shows "No pages match “{term}”".
2. Given a page link, when the page renders, then the link shows the target's icon and current title and opens `/notes/{targetId}` when activated by click or Enter; when the target is renamed, then the link shows the new title the next time the page is read, without the linking page being saved.
3. Given a page link whose target the viewer may not open, or whose target is archived, when the page is read through the API or the UI, then the link reads "Private page", is not a link, and the response holds the `pageId` but never the target's title or icon.
4. Given a save, when it holds page-link spans, then any text sent with them is discarded; a page link already on the page is kept even if the saver can no longer open its target, and a new page link to a page the saver may not open or that does not exist answers 400, with nothing that distinguishes the two.
5. Given a page that other pages link to, when it renders, then the "Linked from" section lists, by icon and title, only the non-archived linking pages the viewer may open, each linking to it; linking pages the viewer may not open are neither named nor counted; with none it reads "No pages link here yet."
6. Given a save that adds or removes page links, when it succeeds, then the page's links are rebuilt from the saved blocks, so a removed link no longer lists the page under "Linked from" on the target, and a new link does.
7. Given an anonymous visitor, when they call the suggestions endpoint, then the response is 401; given a member, then suggestions never include a page they may not open (`L2-092`).

## L2-091: Nested pages, move and breadcrumb
**Traces to:** L1-022

A page may have one parent page that the same owner owns. Nesting changes where a page is shown, never who may open it: each page keeps its own visibility.

**Acceptance Criteria:**
1. Given a page, when it renders, then the breadcrumb reads "Notes › {ancestors} › {title}" from the top-level page down, with "Notes" and each ancestor the viewer may open as links; an ancestor the viewer may not open, or that is archived, reads "Private page" and is not a link.
2. Given a page with child pages, when it renders, then the "Pages inside" section lists, by icon and title, the non-archived child pages the viewer may open, most recently edited first, each linking to it; children the viewer may not open are neither named nor counted; for the owner with no children it reads "No pages inside yet." with "New page inside" (`L2-085` AC7), and for anyone else the section is not shown.
3. Given the owner (or a holder of `AdministerOrganisation`, `L2-098`) chooses "Move", when the move-note dialog opens, then it reads "Move {title}" with "Choose where this page lives. Only your own pages are listed.", a search field "Search your pages", the option "Top level (no parent)" first, then the owner's non-archived pages other than this page and its descendants, and the button "Move"; the current parent is marked "Current".
4. Given a new parent is chosen, when the owner confirms "Move", then `PUT /api/notes/{id}/parent` saves it, the breadcrumb updates, and the toast "{title} moved", "It’s now inside {parent title}." (or "It’s now at the top level.") is shown.
5. Given `PUT /api/notes/{id}/parent`, when the parent is the page itself or one of its descendants, is not owned by the page's owner or is archived, then the API answers 400 and nothing changes; when the caller may not open the page or the parent, or either belongs to another organisation (`L2-130` AC3), then it answers 404.
6. Given the move fails, when the dialog settles, then it shows "Not moved", "We couldn’t reach {organisation short name}. Nothing changed — try again." with "Try again" (`L2-134` AC1), and the page is unchanged; while in flight the button reads "Moving…".
7. Given a page's parent is archived (`L2-095`), when its children are read, then they keep their parent, visibility and content, and their breadcrumbs show the archived parent as "Private page".

## L2-092: Page visibility and access on the server
**Traces to:** L1-022

Every page is Private (its owner and a holder of `AdministerOrganisation`), Shared (named members and/or roles of the organisation; a role audience is live) or Global (every signed-in member of the organisation), as for resources (`L2-060`). Visibility is applied inside every query, within the organisation (`L2-130` AC2): lists, page reads, images, link suggestions, page-link text, search, backlinks, breadcrumbs and "Pages inside". A page the caller may not open behaves as if it did not exist.

**Acceptance Criteria:**
1. Given a Private page, when anyone other than its owner or a holder of `AdministerOrganisation` requests it by page, API, image, list, link suggestion, search, backlink, breadcrumb or "Pages inside", then it is not returned (404 for a direct request, and "Private page" where it is linked, `L2-090`, `L2-091`).
2. Given a Shared page, when its owner, a member named in its audience, a member who currently holds a role named in its audience, or a holder of `AdministerOrganisation` requests it, then it is returned; when anyone else requests it, then it is not returned (404 for a direct request).
3. Given a Global page, when any signed-in member of the organisation requests it, then it is returned.
4. Given a new page, when it is created, then it is Private, and `POST /api/notes` accepts only a title and a parent, so no other visibility can be set on create.
5. Given an anonymous visitor, when they call any Notes endpoint, including an image URL, then the response is 401, and no public URL for a page or an image exists.
6. Given a member who may open a page but does not own it and does not hold `AdministerOrganisation`, when they open it, then `canEdit` is false and the page renders read-only: the blocks show as content with no editable text, handles, slash menu, formatting toolbar, "Share", "Move", "Archive", "Page settings" or "New page inside", and `PUT /api/notes/{id}`, the visibility, parent, archive and image-upload endpoints answer 403.
7. Given a Shared page viewed by a recipient, when it renders, then a banner headed "Shared with you" reads "{Owner} shared this with {you | everyone who has the {role} role}. You can read it, but only {Owner} can change it."; given any other page the viewer may read but not change, such as a Global page viewed by anyone but its owner, then a banner headed "Read only" reads "Only {Owner} can change this page."
8. Given the owner viewing their Private page, when it renders, then a banner reads "Only you can see this. An administrator can too, and every time they open it, it’s recorded in the audit log."
9. Given a page that does not exist, belongs to another organisation (`L2-130` AC3), is archived and the viewer is not its owner or a holder of `AdministerOrganisation`, or is not visible to the viewer, when they open `/notes/{id}`, then the API answers 404 and the page shows "This page isn’t available", "It may have been archived, or it hasn’t been shared with you. If someone sent you the link, ask them to share it with you." and "Browse notes", with nothing that distinguishes the cases.
10. Given a member whose roles carry only view capabilities (seeded as Staff in FaithTech, `L2-151`), when they request pages, then they see exactly what the rules above grant them; no capability other than `AdministerOrganisation` gives read-all access to Private or Shared pages.
11. Given a suspended member, when any request is made with their session, then it is refused (`L2-039`), and their pages stay unchanged and visible to everyone the rules above allow.
12. Given a member's roles change, when they next list, search or open pages, then pages shared with a role they gained are visible and pages shared only with a role they lost are not, without any page being changed (`L2-042` AC4).
13. Given any Notes list, search or suggestion query, when it is built, then the visibility filter is applied in the database query, not after loading the data (`L2-042` AC3).

## L2-094: Edit conflicts
**Traces to:** L1-022

Every page carries an integer version. Every whole-page save sends the version it was based on, and the server never overwrites a newer version.

**Acceptance Criteria:**
1. Given `GET /api/notes/{id}`, when it answers, then it includes the page's current version; given a save whose version matches, when it succeeds, then the response is 200 with the next version, which the next save sends.
2. Given a save whose version does not match the stored one, when it is sent, then the API answers 409 with the current version, the name of who saved it and when, and nothing on the page is changed.
3. Given a 409, when the editor receives it, then autosave stops, editing is paused (the blocks become read-only, while their text can still be selected and copied), and a banner reads "This page changed somewhere else", "{Who} saved a newer version at {time}. Your last changes weren’t saved." with "Reload page", where {Who} is "You" when it was the same member in another tab or device.
4. Given the conflict banner, when the member chooses "Reload page", then the latest version is loaded into the editor, the banner closes, and autosave resumes from that version.
5. Given a conflict, when it happens, then the client never resends the rejected changes with the newer version on its own, so no edit is silently overwritten.
6. Given a save from a caller who can no longer edit the page (for example a holder of `AdministerOrganisation` whose role was removed, or whose definition lost the capability, while editing, `L2-133` AC5), when it is sent, then the API answers 403, editing stops, and a banner reads "You can’t change this page", "Your access changed while you were editing. Your last changes weren’t saved." with "Reload page", which opens the page as the caller may now see it.
7. Given the page was archived or is no longer visible to the caller while they edit, when a save is sent, then the API answers 404 and the editor shows "This page isn’t available" as in `L2-092` AC9.

9. Given any member who is not the owner or a holder of `AdministerOrganisation`, when they call the archive, restore or archived-list endpoints, then archiving a page they can see answers 403, restoring an archived page answers 404 (it does not exist for them, AC2), and the archived list holds only the caller's own archived pages.

## L2-098: Capabilities on pages

Given a holder of `AdministerOrganisation`, when they edit, share, move, archive or restore a page they do not own, then an audit entry is written with the actor, the action (`note.edited`, `note.shared`, `note.moved`, `note.archived` or `note.restored`), the page and the before and after values (version, visibility and audience, or parent), one entry per successful request (`L2-041` AC1), in the organisation's audit log (`L2-130` AC7).

## L2-099: Notes accessibility

## L2-100: The locked view reveals nothing about the product
**Traces to:** L1-023

Design: `docs/detailed-designs/platform/private-preview-wall`.

**Acceptance Criteria:**
1. Given the wall is on and a visitor holds no valid unlock, when they navigate (GET or HEAD accepting `text/html`) to any path on any organisation's community or public host, or on an unknown host, including `/`, `/events/{id}`, `/public/events/{id}` and `/sign-in`, then the response is 403 with the wall page and `Cache-Control: no-store`.
2. Given the wall page, when it is read, then its title and only heading are "Private preview", it says "This site is not open yet. Enter the passphrase to continue.", and it holds one labelled passphrase field and an *Unlock* button; it contains no logo, image, favicon file, product, platform or organisation name, description, `og:`/`description` meta, brand colour or link to the product.
3. ## L2-101: Every path is refused while locked
**Traces to:** L1-023

The wall is enforced by the server in front of everything it serves, ahead of organisation resolution (`L2-131` AC1: wall first, then organisation resolution, then authentication; `docs/detailed-designs/platform/server-authorization` still applies after both).

**Acceptance Criteria:**
1. Given the wall is on and no valid unlock, when any request reaches `/api/*` (including the public event, guest RSVP and `.ics` endpoints), `/connect/*`, `/.well-known/*`, `/hubs/*` (negotiate and WebSocket upgrade), a static file of the community or marketing app on any organisation's host (scripts, styles, images, video, `favicon.ico`, source maps) or an unknown path, then it is refused as `L2-100` AC1 or AC5 describes and never reaches organisation resolution, routing, authentication or the apps.

3. Given no valid unlock, when a CORS preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) arrives from the public or community origin of the organisation the request host belongs to (`L2-131` AC6), then it is answered by the CORS policy (preflights carry no cookies); from any other origin, including another organisation's, it is refused with 403.
4. Given a valid unlock, when the same requests arrive, then they behave exactly as without the wall: the host resolves its organisation (`L2-131`), anonymous endpoints stay anonymous, and every endpoint keeps its authentication, capabilities and permission rules (`L2-042`, `L2-135`). Public events stay public only to visitors past the wall.
5. Given a valid unlock cookie set for the parent domain, when a request arrives on any other host under the cookie domain (another organisation's host, or www after unlocking on app, or the reverse), then it is let through (`L2-104` AC3).

## L2-102: Unlock with the owner passphrase
**Traces to:** L1-023

**Acceptance Criteria:**
1. Given the wall page, when the owner submits the correct passphrase with the form's CSRF token, then the response is `303 See Other` to the `returnUrl` the form carried and sets the unlock cookie (`L2-104`).
2. Given a `returnUrl` that is not a local path (absolute, scheme-relative `//`, backslash, control characters or over 2,048 characters), when the unlock succeeds, then the redirect goes to `/`.
3. Given a wrong passphrase, an empty or missing passphrase, a passphrase over 1,024 characters, a missing or mismatched CSRF token, or an `Origin` header naming another host, when the form is submitted, then every one of them gets the identical response: 403, the wall page with "That passphrase didn’t work. Check it and try again." under the field, no cookie but a fresh CSRF token, and the same body length.
4. Given the stored secret, when a passphrase is checked, then it is compared with a salted, slow hash (PBKDF2-HMAC-SHA256, at least 600,000 iterations) in constant time, and the hash is computed even when the CSRF check has already failed, so the time taken does not reveal which check failed.
5. Given the server cannot check the passphrase (the hash check throws), when the form is submitted, then the response is 500 with the wall page and "Something went wrong · Try again in a moment." and no detail.
6. Given JavaScript, when the form is submitted, then the button reads "Checking…" with `aria-busy="true"` and further presses do nothing.
7. Given the wall is on, when the API starts without a valid passphrase hash or signing key, then it refuses to start (fails closed).

## L2-103: Brute-force protection
**Traces to:** L1-023

**Acceptance Criteria:**
1. Given 5 refused attempts from one client IP address within 15 minutes, when that address submits again, then it is locked out: the response is 429 with the wall page and "Too many attempts · Wait a few minutes, then try again.", and the passphrase is not checked, so even the correct one is refused.
2. Given an address is locked out, when the lockout ends and it fails 5 more times, then the next lockout is twice as long: 1, 2, 4, 8 … minutes, never more than 60; a success, or 24 hours without a refusal, resets it.
3. Given 100 refused attempts from all addresses within 15 minutes, when anyone submits, then every address is locked out for 15 minutes (a global lockout), doubling on each repeat up to 4 hours.
4. Given a refused or locked-out attempt, when it is logged, then the log records the outcome, the client address and the recent-failure count, and never the passphrase, its length, the CSRF token or the cookie; the request body is never logged.
5. Given the API sits behind the Azure Container Apps ingress, when it reads the client address, then it uses the last `X-Forwarded-For` entry the ingress appended, never one the client sent.

## L2-104: The unlock cookie
**Traces to:** L1-023

**Acceptance Criteria:**
1. Given a successful unlock, when the cookie is set, then it is named `__Secure-unlock`, is `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, has `Max-Age` of 7 days, and holds a token signed with HMAC-SHA256 that carries its own expiry.
2. Given `PrivatePreview:CookieDomain` is `faithtech.community` (the configured example), when the cookie is set on any organisation host under that domain, then its `Domain` is the parent domain, so one unlock covers every organisation's community and public host under it (consistent with ADR 0018's same-site model); with no domain configured (development) the cookie is host-only, and an organisation host outside the cookie domain needs its own unlock.

4. Given the wall page, when it is served, then it sets a CSRF cookie `__Host-wall` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, host-only, no `Domain`) whose random value is echoed in the form.

## L2-105: Revocation and passphrase rotation
**Traces to:** L1-023

**Acceptance Criteria:**

## L2-139: Last administrator and consequences of role changes
**Traces to:** L1-026, L1-014

# L2 - Detailed Requirements

Every acceptance test must start with a header naming the L2s it covers, for example `// Traces to: L2-012`.

Viewport names: XS <576px, SM >=576px, MD >=768px, LG >=992px, XL >=1200px.

---

## L2-001: Sign up
**Traces to:** L1-001

Anyone can create an account with a name, email and password. New accounts have no role.

**Acceptance Criteria:**
1. Given an unused email and a valid password, when the visitor submits the sign-up form, then the account is created with no role, an email-verification message is sent, and the visitor sees the verify-email page.
2. Given an email already registered, when the visitor submits, then the system shows the same "check your email" outcome without revealing that the email exists.
3. Given a password shorter than 12 characters or found in a breached-password list, when the visitor submits, then the form shows an inline error on the password field and no account is created.
4. Given an empty or malformed field, when the visitor submits, then each invalid field shows an inline error, focus moves to the first invalid field, and the error is announced to screen readers.
5. Given the form is submitting, when the request is in flight, then the submit button is disabled and shows a busy state.
6. Given a name longer than 100 characters after trimming, when the visitor submits, then the name field shows "Use 100 characters or fewer for your name." and no account is created, so every new name can be saved unchanged in the profile editor (`L2-006`).

## L2-002: Email verification
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given a valid, unexpired verification link, when the user opens it, then the email is marked verified and the user is taken to set up their profile.
2. Given a verification link older than 24 hours or already used, when the user opens it, then an error page offers to resend the link.
3. Given an unverified account, when the user signs in, then they can browse, but a banner asks them to verify their email and offers a resend, and RSVPing, creating content and sending invites are refused until the email is verified.
4. Given a resend request, when more than 3 resends have been requested in the last hour, then the request is rejected with a "try again later" message.

## L2-003: Sign in and sign out
**Traces to:** L1-001

The Angular app signs in with OAuth2 authorization code + PKCE against OpenIddict.

**Acceptance Criteria:**
1. Given a verified account and correct credentials, when the user signs in, then an authorization code is exchanged with PKCE for tokens, and the user lands on the page they first requested, or the home page.
2. Given incorrect credentials, when the user signs in, then a generic "email or password is incorrect" error is shown.
3. Given 5 failed attempts within 15 minutes, when a 6th is made, then the account is locked out for 15 minutes; failed attempts older than 15 minutes, or made before a successful sign-in, a password reset or an elapsed lockout, do not count.
4. Given a suspended account, when the user signs in, then sign-in is refused with a "your account is suspended" message.
5. Given a token request without a valid PKCE code verifier, when it reaches the token endpoint, then it is rejected.
6. Given a signed-in user, when they sign out, then their tokens are revoked, and any further API call with those tokens returns 401.
7. Given an expired access token and a valid refresh token, when the app calls the API, then the token is refreshed silently.
8. Given "Keep me signed in on this device" is not ticked, when the browser session ends, then the refresh token is discarded and the user must sign in again.
9. Given a signed-in user on any page and at any width, when they open the account menu from their avatar in the top bar, then it offers "Your profile", "Settings" and "Sign out", and "Sign out" ends the session on this device as in criterion 6.

## L2-004: Password reset
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given any email, when the user requests a reset, then the same confirmation message is shown whether or not an account exists, and an email is sent only if it does.
2. Given a valid reset link younger than 1 hour, when the user sets a new valid password, then the password is changed, every existing session for that account is revoked, and the user can sign in.
3. Given an expired or already-used reset link, when the user opens it, then an error offers to request a new link.

## L2-006: Edit own profile
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a signed-in user, when they change their name, home city or bio and save, then the profile updates and a success toast is shown.
2. Given an empty name or a name longer than 100 characters, when they save, then an inline error is shown and nothing is saved.

## L2-007: Profile photos
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given a JPEG, PNG or WebP file of 5 MB or less with alt text, when the user uploads it, then it is resized on the server, stored in blob storage with metadata removed, and shown on the profile within 5 seconds.
2. Given a file larger than 5 MB, of another type, or whose content does not match its extension, when the user uploads it, then it is rejected with an inline error.
3. Given empty alt text, when the user uploads, then the upload is blocked with "Describe this photo".
4. Given a profile with 10 photos, when the user tries to add another, then the upload control is disabled and explains the limit, and the API rejects the upload.
5. Given several photos, when the user marks one as featured, then it becomes the only featured photo.
6. Given the featured photo is deleted after confirmation, when other photos remain, then the most recently uploaded remaining photo becomes featured.
7. Given an uploaded photo, when the owner changes its description to non-empty text and saves, then the new alt text is stored; an empty description is blocked with "Describe this photo".
8. Given blob storage is unavailable, when the user saves a valid photo, then the photo is kept with its description, counts towards the 10-photo limit and the featured rule, is shown as "Saved. It shows on your profile once it finishes storing.", and appears without uploading again once storage recovers; a photo deleted while storage is down is removed at once and its blob is deleted later (`L2-047`).

## L2-009: Role assignment limits
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a City Lead, when they add or remove Event Lead, Create Lead, Communications Lead, Volunteer, Product Engineer or Attendee on any profile, then the change succeeds and the profile owner is notified.

5. Given a removal, when the add-role or remove-role dialog is confirmed, then the profile's roles update without a page reload.
6. Given the last System Admin, when anyone tries to remove that role, then the change is refused.

## L2-026: Global search

## L2-028: Email notifications
**Traces to:** L1-010

These emails are sent: a contact signed up, an event cancelled or changed, invites, RSVP confirmations, role changes, Agile assignments and workspace additions, Planning Poker invitations, and announcements. Only announcement emails can be turned off.

**Acceptance Criteria:**
1. Given a triggering action, when it completes, then the email is queued and sent within 2 minutes, retrying on failure for up to 5 delivery attempts in all, counting the first send, after which it is marked failed and not retried.
2. Given an email, when it is rendered, then it includes a plain-text part, and every link uses HTTPS.
3. Given a user who opted out of announcement emails, when an announcement is sent, then no announcement email reaches them, but other notification emails still do.

## L2-031: Agile workspaces and membership
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given a City Lead, when they create a workspace with a name and a method (Scrum or Kanban), then they become its owner. A City Lead can own more than one workspace.
2. Given the owner, when they add members, then only profiles holding a lead or volunteer role can be chosen, and each added member is notified.
3. Given a member, when they open the workspace, then they can create and edit stories and tasks, move cards, comment and vote in Planning Poker. Only the owner creates and edits initiatives and epics.
4. Given a member who is not the owner, when they try to manage members, change settings, manage sprints, or archive the workspace, then the control is hidden and the API returns 403.
5. Given Staff, when they open any workspace, then they can view it but every write returns 403.
6. Given a non-member who is not Staff or System Admin, when they request the workspace or its items, then the response is 404, and nothing appears in their search.
7. Given a System Admin, when they act on any workspace, then the action succeeds and is audited.
8. Given a removed member, when the removal completes, then their assigned items become unassigned.

## L2-038: Planning Poker sessions
**Traces to:** L1-013

**Acceptance Criteria:**
1. Given a member, when they start a session for one or more stories and invite workspace members, then they become the facilitator, the invited members are notified in-app and by email, and the stories are estimated one at a time.
2. Given an open session, when members vote from the deck 1, 2, 3, 5, 8, 13, 21 or ?, then other participants see who has voted, but not the values, within 2 seconds, using SignalR.
3. Given the facilitator, when they reveal, then all votes are shown to everyone.
4. Given revealed votes, when the facilitator starts a re-vote, then the previous votes are cleared.
5. Given the facilitator sets the final points, when they save, then the story's points update.
6. Given a non-facilitator, when they try to reveal, re-vote or set the points, then the action is refused.
7. Given a user who is not a member, when they try to join, then they are refused. Staff can watch but not vote.
8. Given a lost connection, when it is restored, then the participant rejoins with their current vote intact.
9. Given a participant who has voted, when they press their chosen card again before the reveal, then their vote is withdrawn and other participants see them as still choosing.
10. Given a vote that reaches the server after the votes are revealed, when it is refused, then the voter sees why under the deck and the vote is not counted; a vote that fails to send leaves the previous vote standing and the voter is told so.

## L2-041: Audit log
**Traces to:** L1-014

**Acceptance Criteria:**
1. Given any System Admin action, or any role change, when it completes, then an audit entry stores the actor, the action, the target, the before and after values, the time in UTC, and the IP address.
2. Given the audit log, when a System Admin views it, then it shows when, who and what for the last 90 days by default, can be filtered by category (role changes, suspensions, private contact access, deletions), and is paged 50 at a time.
3. Given any user, when they try to edit or delete an audit entry, then no API exists to do so, and the entry is unchanged.
4. Given a user who is not a System Admin, when they request the audit log, then the response is 403.
5. Given the audit log, when a System Admin chooses "Export CSV", then the filtered entries are downloaded.
6. Given an export in progress, when the file is being prepared, then "Export CSV" is busy and cannot be pressed again; when the download is ready, a success toast "Audit log exported" confirms it; when it fails, a danger toast "We couldn’t export the audit log" offers "Try again".

## L2-042: Authorization on the server
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given any API endpoint, when it is called without authentication, then the response is 401, except for the endpoints explicitly marked anonymous: public events, guest RSVP, sign-up, sign-in, password reset, verification, invite acceptance and announcement unsubscribe.
2. Given a resource the caller is not permitted to see, when it is requested by ID, then the response is 404, not 403, so that its existence is not revealed.
3. Given a list, search or export, when it is built, then the permission filters are applied in the database query, not after loading the data.
4. Given a role added to or removed from a user, when that user next calls the API, including with an access or refresh token issued before the change, then the server authorizes with the profile's current roles, and `/api/me` reports them.

## L2-043: Input validation and web protections
**Traces to:** L1-015

**Acceptance Criteria:**
1. Given any request body, when it fails validation, then the response is 400 with problem details per field, and nothing is saved.
2. Given user-entered text, when it is rendered, then it is encoded, and script injection does not execute.
3. Given any response, when it is sent, then it carries HSTS, a Content-Security-Policy without unsafe-inline scripts, X-Content-Type-Options and frame protection.
4. Given a state-changing request from another origin, when it arrives, then CORS rejects it.
5. Given more than 100 requests per minute from one user, or 20 per minute from one IP address to the auth endpoints, when another arrives, then the response is 429.
6. Given the repository and logs, when they are inspected, then no secrets, passwords or tokens appear in them.

Textarea

Several lines of text: a bio, an event description, an announcement, a private note on a contact. Same look and states as the text field, taller.

Overview

A textarea takes text that can run to several lines: a profile bio, an event description, an announcement, a note on a contact, a comment on a work item, the reason for suspending someone. It is a textarea.textarea inside a form field, and shares every state and token with the text field.

  • Free text (most uses): optional, prefilled when editing ("Bio", "Description", "First note").
  • Required message: the text is the point of the action and cannot be empty ("Message" on an announcement, "Message to attendees" when cancelling an event, "Reason (recorded in the audit log)" when suspending).
  • Inline composer: a short textarea with a small primary button below it, on a contact ("Add a note") and a work item ("Add a comment"). The textarea is the composer’s only field and the button does nothing without it, so it is required and its label carries no "(optional)".

Anatomy

  1. LabelFrom the form field, with "(optional)" when it is.
  2. Text areaAs tall as its rows, --line-height-relaxed, same border, radius and background as the text field.
  3. Resize handleVertical only (resize: vertical), so the field never breaks the layout width.
  4. Help or errorFrom the form field: the length limit, or how to fix the message.

Sizes

The height is set by rows alone, with no minimum height, so 2 rows render shorter than 3. The mocks use 2 rows for composers and short notes (invite "Personal note", "Add a comment"), 3 for dialog messages and first notes, 4 for bio and descriptions, 6 for the announcement message. People can drag it taller.

2 rows (send invite) and 6 rows (compose announcement).

Both themes

  • Invalid appears on submit when a required message is empty: "Tell attendees why, so they aren’t left guessing.", "Give a reason so other admins understand.", "Write a message of at least one sentence."
  • Busy is not a textarea state: while the form submits, the text stays editable and only the buttons lock.
  • Read-only and disabled are not used in the mocks; shown for completeness.
Give a reason so other admins understand.

With a character counter

A textarea with a limit (the 400-character bio) shows a .field__count line under it that counts down as the person types. Past the limit it says how many characters to remove and turns danger with .field__count--over; nothing is cut off, and saving shows the field error (edit-profile/default, edit-profile/invalid).

Responsive behaviour

  • Full width of its form or dialog; the height does not change with the viewport.
  • In a bottom-sheet dialog on a phone, the dialog body scrolls; the textarea does not grow past the sheet.
  • Text is 16px, so iOS does not zoom on focus.

Theming

Shares --field-bg and --field-border with .input, so every state and both themes match the text field exactly. The only textarea-specific values are the minimum height and --line-height-relaxed.

Accessibility

Role and pattern

Native <textarea> with a <label for>. Help and errors are joined by aria-describedby; required messages use the native required attribute.

Keyboard

KeyAction
TabMoves into the textarea. Tab never inserts a tab character.
EnterInserts a new line. It never submits; the composer submits with its button.

Focus

The shared focus ring with no offset, and the border takes the ring colour.

Labelling

Every textarea has a visible label that says what to write: "Message to attendees", not "Message". A limit is in the help text, so it is read before typing. The counter is joined by aria-describedby and is not a live region, so it is read on focus, not on every keystroke.

Motion

Border colour fades over --duration-fast; reduced motion makes it instant.

Touch

The text area is well over the target size. The resize handle is a convenience only; nothing depends on it.

Content

  • Label what to write and who reads it: "Message to attendees", "Note for the history", "Reason (recorded in the audit log)".
  • Say who can see private text in the help or nearby copy: contact notes are visible only to the lead who wrote them and System Admin.
  • State a limit in help ("Up to 400 characters.") rather than cutting text off, and count it: "272 characters left", "1 character left", "37 characters too many".
  • Prefill with a useful draft only when the product knows one; never with placeholder filler.

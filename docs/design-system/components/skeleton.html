Skeleton

Grey shapes in the layout of the page that is coming, with a soft shimmer. They show where contacts, events, partners and audit entries will appear, so the page does not jump when the data arrives.

Overview

Every FaithTech page with a loading state uses skeletons for its first load: Home, Contacts, Events, Partners, Team, People, the audit log, workspaces, the board and the backlog. Keep the real page chrome (top bar, page header and title, tabs, filters and buttons that work without data, such as Add contact or Export CSV) and swap only the data for skeletons.

  • For an action in progress (Send invite, Save profile), use a busy button or an inline status, not a skeleton.
  • If loading fails, replace the skeletons with an error empty state ("We couldn’t load your contacts").

Anatomy

  1. Avatar circle.skeleton.avatar.avatar--sm: the avatar's exact size and round shape, shimmer instead of initials.
  2. Title bar.skeleton--title: 1.5em tall, 40% wide; stands for the name.
  3. Text line.skeleton--text: 1em tall; the last line is 60% wide; stands for the meta line.
  4. Busy containerThe real list card with aria-busy="true" and an aria-label that says what is loading.

Sizes

Text and title skeletons are sized in em, so they follow the font size of where they sit. Blocks take a height that matches the real content (4rem for a partner or story card). Avatar skeletons reuse .avatar--sm for list rows and .avatar--xl for the profile header. The Home subtitle uses an inline text skeleton 12rem wide.

States

A skeleton has one state, loading. The container moves from loading to loaded (or to an error).

Both themes

  • Loaded: remove aria-busy and the aria-label, and swap skeletons for content in one paint, so screen readers read the finished section once.
  • Failed: replace the whole section with an error empty state ("We couldn’t load your contacts").

Responsive behaviour

  • Skeletons live inside the real layout (list card, .split, .grid--auto, .kanban), so they reflow exactly as the content will. The Kanban skeleton scrolls sideways on phones like the real board.
  • Show the number of placeholders that fills the first screen: three or four list rows, two cards per Kanban column. Do not draw a whole list.
  • Fixed widths (the 12rem Home subtitle line) stay below 320px so they never overflow a phone.

Theming

The shimmer is a gradient between --color-bg-subtle and --color-bg-subtle-hover, both tuned per theme, so skeletons are quiet grey on light cards and a lifted grey on dark ones. .avatar.skeleton drops the avatar's colour and initials.

Accessibility

Role and pattern

Every skeleton is aria-hidden="true". The section that is loading carries aria-busy="true" and an aria-label ("Loading contacts", "Loading partners", "Loading audit log"), so assistive tech knows it is not ready and does not read half a page.

Keyboard

KeyAction
TabSkips skeletons. Real controls in the chrome (Add contact, Archived, the search field, the audit-log Action filter) stay reachable while the data loads.

Focus

Skeletons never take focus. When content arrives, focus stays where it was.

Labelling

The busy container says what is loading in words. Keep the page <h1> real ("Contacts", "Good afternoon"); where the heading itself is data, as on a profile, keep a visually hidden <h1> ("Profile") so the page is identified from the start.

Contrast

Skeletons are decorative placeholders and are exempt from 1.4.11. The real text that replaces them uses the normal pairs:

Loaded text on card
Loaded meta on card

Motion

The shimmer runs once per --duration-loop (1.4 s). Under prefers-reduced-motion the animation is removed and the skeleton is a flat grey shape.

Touch

No targets.

Content

  • The busy label is "Loading" plus the thing: "Loading contacts", "Loading your events", "Loading profile", "Loading audit log".
  • Never put text inside a skeleton or show "Loading…" over it; the shapes are the message.

Capability checklist

A checkbox per catalogue entry with its description, laid out in two columns, with a disabled state that keeps its reason readable. Used by the define-role and grants dialogs.

Overview

The capability checklist offers every entry of a fixed catalogue as a checkbox with a one-line description: the platform's nineteen capabilities in the define-role dialog, and the organisation's roles in the grants dialog. It is a checkbox group laid out as a grid, with a per-entry disabled state that keeps its reason readable.

  • Use it when every option needs a description to be chosen well, and there are more than six options.
  • Use a plain checkbox group for short pickers (members, stories).
  • It knows no capability or role name: the entries arrive as data (value, label, description, disabledReason).

Anatomy

  1. Legendlegend.field__label: “Capabilities”, or “Holders of {role} may add and remove:”.
  2. CheckboxNative checkbox, square, as the checkbox group.
  3. Label and description.choice__text with a small description from the catalogue.
  4. Second columnFrom 48rem the grid has two columns; below, one.

Variants

Capabilities
Two columns (.capability-checklist): the define-role dialog's Capabilities.
Holders of City Lead may add and remove:
Single column (--single): the grants dialog, where a disabled entry carries its reason.

Sizes

Not applicable. One size; the grid changes columns, not the row size.

States

UncheckedCheckedDisabled with reasonInvalidBusy (all disabled)
  • Disabled with reason: the description is replaced by the reason (“Only administrators can grant administration”) and stays in --color-fg-muted, so the reason passes contrast while the label greys out.
  • Invalid: a server refusal for one entry (400 in the grants dialog) sets aria-invalid on that checkbox and shows a .field__error under it.
  • Busy: the whole group is disabled while the dialog saves.

Responsive behaviour

  • One column below 48rem, two from 48rem (--single keeps one).
  • Long lists scroll inside the dialog body, never the page; the dialog footer stays sticky.

Theming

The checkbox group's tokens in both themes. The disabled reason keeps --color-fg-muted rather than --color-fg-disabled.

Accessibility

Role and pattern

Native checkboxes in a fieldset with a legend; no ARIA roles. A grid layout does not change reading order: entries read row by row in catalogue order.

Keyboard

KeyAction
Tab / Shift+TabMoves between enabled checkboxes; disabled ones are skipped.
SpaceChecks or unchecks.

Labelling

Label and description are the checkbox's name, so the reason of a disabled entry is read with it.

Touch

The whole row is the target, at least --target-min tall.

Content

  • Labels are verb phrases in sentence case: “Manage events”, “Assign roles”.
  • Descriptions say what the holder can do, in one sentence ending with a full stop.
  • A disabled reason says who can: “Only administrators can grant administration”.

Code

<fieldset class="capability-checklist">
  <legend class="field__label">Capabilities</legend>
  <label class="choice"><input type="checkbox" value="ManageEvents" checked>
    <span class="choice__text">Manage events<small>Create, edit and cancel events.</small></span></label>
</fieldset>

In Angular: <ft-capability-checklist legend="Capabilities" [entries]="entries" [formControl]="selected" [single]="false">, where each entry is { value, label, description, disabledReason? }. Built on CheckboxGroupComponent; the value is the array of checked values.

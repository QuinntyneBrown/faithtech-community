Event hub sections

An event hub is made of sections, each with a fixed shape and a fixed layout. Every section has one display that renders it on the hub, in the section preview and on a wizard’s review step. The displays are composition in the events library, built only from components-library primitives; there is no page builder and no styling panel.

Overview

The hub home lists the sections as checklist rows. Fill in or Edit opens that section’s wizard (a dialog, with a stepper for the two-step Agenda and People); the row’s “More for {Section}” menu offers Preview and Hide section; Reorder on the Sections card opens “Reorder sections”, a reorderable list.

The seven display components (hub-hero, hub-agenda, hub-venue, hub-people, hub-links, hub-giving, hub-upcoming) live in frontend/projects/events. They add no new library component. The only new rules are the agenda’s time column and its out-of-hours warning, .hub-section__time and .hub-section__warning in assets/components.css.

When to use

  • For every section of an event hub: on the hub itself, in the "{Section} preview" dialog and on the review step of the Agenda and People wizards.
  • Not for the hub home: that is the checklist of checklist rows, which shows each section's state, not its content.
  • Each new section kind gets a display of its own, documented here and composed the same way: slice 46 adds the ten optional displays.

Structure

  1. Section: <section class="hub-section"> labelled by its heading; a column with --space-3 between parts.
  2. Heading: h3.section-title on the hub (the hub page owns the h1 and h2s). In the preview dialog and a review step the dialog title names the section, so the display drops its heading.
  3. Body: library primitives only: list, avatar, badge, description list, event card, card, button and link.
  4. Live values: anything the system knows (event, organisation, members, upcoming events) is read when the hub is read, never copied into the section (design rule 4).

The ten optional displays

Slice 46 (L2-172 to L2-183) adds ten optional section kinds. A hub always has the seven core sections; it has an optional one only when its starting point brings it (a template that names it, or a copied hub that has it). The catalogue order is fixed: Hero, Agenda, Venue, Parking, What to bring, Partners, Tracks, Process, Rules, People, Submission and feedback, Demo format, Judging and honors, Worship, Slides, Giving, Upcoming events. Each optional kind is Ready when it has at least one item. Parking maps and slides are resources the hub names; a visitor reaches them only through the hub’s file links, and only for a shown section.

Like the core seven, each display is composition in the events library. Slice 46 adds the library pieces they need: the slide viewer, the numbered list and initials icon tile, the media card, the stacked description list and the stacking table; the wizards add the live total. Examples below are the SoCal hackathon’s content (pages/hub-page/hackathon).

The hub home with optional sections

The hub home lists the hub’s own sections only, in its order: seven for a Blank hub, seventeen for a hub started from Hackathon. Each new row uses the same checklist row with its line (“Where to park, with a map and notes for each option.”) when Ready and its Needs info line (“Add a parking option.”) otherwise; Fill in and Edit open that kind’s wizard. Hidden rows stay listed and are left out of the count (“12 of 16 sections ready”). Step 3 of Create event hub lists the same sections, ticked for the template (dialogs/create-event-hub/sections-from-hackathon).

The ten wizards

Each optional kind has a wizard in the house style of Agenda and People: a CDK dialog over ft-dialog, with an ft-stepper when it has two steps (Parking, What to bring, Tracks, Process, Judging and honors); Preview on every step; Save and Back; “Saving…” while busy; the failed alert “We couldn’t save this section” with Try again; and the toast “{Title} saved” on the hub home. Rows of items use Add, Remove, Move up and Move down. Images and slides come from “Choose from Resources” (a shared resource picker dialog with search and thumbnails) or an upload, which adds a shared resource. Demo format and Judging show a live total.

States

A display renders only a Ready section. A Needs info section is never published: the hub leaves it out and its checklist row says what is missing. A Hidden section is not rendered at all, and its content is kept until it is shown again.

<!-- events library: hub-agenda.component.html, live on the hub page (live = true), plain in the preview dialog -->
<section class="hub-section" [attr.aria-labelledby]="id">
  <h3 [id]="id">Agenda</h3>
  @if (live() && timeline().finished) { <p class="text-muted">This event has finished.</p> }
  <ft-list label="Agenda">
    @for (row of rows(); track $index; let i = $index) {
      @let state = live() ? timeline().states[i] : 'plain';   <!-- 'finished' | 'current' | 'next' | 'plain' -->
      <ft-list-item [label]="row.title" [description]="row.detail"
                    [state]="state === 'current' ? 'current' : state === 'finished' ? 'finished' : 'default'"
                    [attr.aria-current]="state === 'current' ? 'time' : null">
        <span leading class="hub-section__time">{{ row.time }}</span>
        @switch (state) {
          @case ('current') { <ft-badge meta variant="success">Happening now</ft-badge> }
          @case ('next') { <ft-badge meta>Up next</ft-badge> }
          @case ('finished') { <span meta class="visually-hidden">Finished</span> }
        }
      </ft-list-item>
    }
  </ft-list>
  <p class="visually-hidden" role="status" aria-live="polite">{{ announcement() }}</p>
</section>

// hub-agenda.component.ts (sketch)
readonly live = input(false);
private readonly now = signal(this.clock.now());          // injected clock, faked in tests
constructor() {                                            // re-check every 30 seconds; nothing moves on screen
  const timer = setInterval(() => this.now.set(this.clock.now()), 30_000);
  inject(DestroyRef).onDestroy(() => clearInterval(timer));
}
// Each row runs from its start instant to the next row's start; the last row to the event's end.
// Instants are compared, so the highlight is right in any time zone; times are shown in the visitor's zone.
readonly timeline = computed(() => agendaTimeline(this.rows(), this.eventEndsAt(), this.now()));
// Announce only when the current row changes after first load: "Happening now: {title}" or "This event has finished."
readonly announcement = linkedSignal<..., string>({ source: () => this.timeline().currentKey,
  computation: (key, previous) => previous === undefined ? '' : this.timeline().spoken });

Starting a hub

Step 2 of Create event hub (“Starting point”) asks one question, “How do you want to start?”, and step 3 (“Sections”) shows the answer’s result before anything else is asked. Slice 45, L2-169 to L2-171.

  • Order: the organisation’s templates, in its order, each with its one line; then the built-in Blank (the default) and Copy a past hub. Templates are organisation data: FaithTech’s Hackathon, Meetup and Workshop are seed, never code.
  • Copy a past hub asks its follow-up in the same step: “Search past hubs” and “Which hub?” (see Radio group, a choice that asks a follow-up). Nothing picked is “Choose a hub to copy.” on Next.
  • Next applies the choice (save as you go): the primary button reads “Saving…” and the step is disabled; a failure keeps the choice and offers Try again. Going Back and choosing again replaces what the first choice filled.
  • Step 3 is pre-ticked by what was applied: a template’s shown sections, or the copied hub’s. The hint names the source first: “Ticked for Meetup.” or “Ticked for the hub you copied.”, then “Untick anything you don’t need. You can change this later.” After Blank it keeps the plain hint and every section ticked.
  • Templates fill default text (the Hero subtitle, agenda rows timed from the event’s start, the Giving line, how many upcoming events), so those sections arrive Ready on the hub home; copying brings every section with its agenda and code-freeze times moved by the difference between the two events’ starts.
  • The templates fail to load: Blank and Copy a past hub stay, under a danger alert “We couldn’t load the templates” with Try again. The step never blocks.

Responsive behaviour

  • Every display is one column at every width and fills the hub’s content column; nothing scrolls sideways at 360px.
  • The agenda time column narrows from 4.5rem to 3.75rem under 40rem; titles and details wrap beside it.
  • Hero: the body wraps under the eyebrow; the RSVP button stays at least 44px tall.
  • People and Upcoming events stay lists, not grids, so names and meta lines never truncate.
  • In a dialog (preview, review step) the display uses the wide dialog on tablet and desktop and the bottom sheet on a phone.

Accessibility

  • Each display is a <section> named by its h3; People’s groups are lists named by their group headings.
  • On the hub page the current agenda row has aria-current="time" and the visible badge “Happening now”; finished rows say “Finished” to screen readers; colour is never the only signal. A polite live region announces only a change of current row (Live agenda).
  • Links say where they go: “Submit your project”, “Give feedback”, “Open in maps”, “RSVP”, “Give”. Links that open a new tab say so to screen readers.
  • Avatars are decorative (aria-hidden); the name next to them is the text.
  • In the wizards, every move in a reorderable list is announced politely (“Moved Doors open down to position 2 of 5.”, “Moved Agenda down to position 3 of 7.”), and every field error is tied to its field with aria-describedby.
  • Light and dark come from the tokens; there are no fixed colours.

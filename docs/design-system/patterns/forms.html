Forms

A FaithTech form asks only for what is needed, marks what is optional, checks the answers when the person presses the main button, and keeps everything they typed when something goes wrong.

WCAG 2.2 AAStatus: stablePattern

Overview

Forms are built from text field, textarea, select, switch and button, each inside a .field. There are two places a form can live:

  • Page forms, in a .card.stack capped by .form-width--sm (40rem), --md (44rem) or --lg (48rem): sign up, sign in, the contact form, the partner form, the event form, edit profile, compose announcement and settings.
  • Dialog forms, with one to four fields: send invite, add role, add note, create workspace, new work item, start sprint. Add partner is the one longer dialog form: two required choices (organisation, stage) followed by optional fields in a scrolling body, so a lead can add a partner without leaving the board. See dialogs and overlays.

Pages never have inline edit forms. An Edit button opens a dialog or goes to the form page.

When to use

SituationUse
Five or more fields, uploads, or something worth a URLA page form: contact, partner, event, profile, announcement
One to four fields, on top of what the person is looking atA dialog form: invite, role, partner, sprint
A setting that applies straight awayA switch inside the settings form, saved with Save settings
Searching or filtering a listA role="search" form or a filter select. These are not covered by the validation rules on this page.

Structure

Each field has a label, then help text if needed, then the control, then the error. Optional fields say "(optional)" in the label, in a .optional span (--color-fg-subtle). Required fields have no marker, because most fields are required. Actions sit in .form-actions: the primary button first, then Cancel as a ghost link.

States

Invalid, with an error summary

When the person presses the main button, the form is checked. If anything is wrong, a danger alert at the top lists each problem as a link to its field, and focus moves to that alert. Each field shows its own error and has aria-invalid. The page title starts with "Error:".

StateBehaviour
DefaultNo errors are shown before the first submit. Fields are not checked while the person types.
InvalidAn error summary and errors on each field. After the first submit, each error clears as soon as its field is fixed.
BusyThe main button gets aria-busy and aria-disabled, a pulsing dot and an "-ing…" label (Saving…, Sending…, Creating account…). Pressing it twice does nothing.
Error (server)A danger alert at the top says that nothing was saved and what to do. Every value is kept.
DuplicateAn info alert explains the match, and the main button changes to fit it ("Save and link").
SuccessEither go to the saved item with a toast, or show a .card--success with what happened and the next steps.

Responsive behaviour

  • One column at every width. Fields that belong together, like Starts and Ends on the event form, sit side by side from 640px and stack below that.
  • Form cards are at most 40rem wide (.form-width--sm; --md, 44rem, for settings and compose announcement; --lg, 48rem, for edit profile and the event form), so lines stay short.
  • Under 640px the buttons in .form-actions fill the width, with the primary button on top.
  • Inputs use the right type and autocomplete (email, tel, new-password, datetime-local), so phones show the right keyboard.

Accessibility

  • Every control has a visible <label for>. Placeholders are only used for search hints.
  • Help text and errors are linked with aria-describedby. The help id comes before the error id.
  • The error summary has role="alert" and tabindex="-1", and gets focus. Each item links to its field (WCAG 3.3.1 and 3.3.3).
  • Errors are text with a danger colour. They never rely on colour alone, and the invalid border meets 3:1.
  • Forms use novalidate, so our messages replace the browser's own bubbles. The server checks everything again and returns the same messages.
  • Password fields allow paste and password managers (WCAG 3.3.8, Accessible Authentication).

Content

  • Labels are short nouns: Name, Email, Venue address, Join with role. The help text gives the reason: "If they ever sign up with this email, we’ll let you know."
  • Errors say how to fix it, not what went wrong: "Enter an email like name@example.org.", "The end time must be after the start time.", "Use at least 12 characters. A short phrase is easiest to remember."
  • The summary counts the problems: "Fix 2 things to save". Its items are short commands: "Enter a name".
  • Buttons say what happens: Save contact, Send invite, Create account, Publish event. Never "Submit".
  • Sign-in errors don't say which part was wrong: "Email or password is wrong. Check both and try again."

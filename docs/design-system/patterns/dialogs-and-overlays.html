Dialogs and overlays

FaithTech Community uses two overlays. A modal dialog, built on Angular CDK Dialog, handles a short decision or a short form in context. The bell panel shows recent notifications. Anything longer, or anything worth linking to, gets its own page.

Overview

The rules in AGENTS.md say there are no inline forms on pages. Any edit started from a button either opens a CDK dialog or goes to its own screen. The mocks have 23 dialogs, and they come in three kinds:

  • Short forms, with one to four fields: Invite someone to FaithTech, Add a role, Add a partner, Start a sprint, New work item.
  • Confirmations that can be undone: Archive Tomás Ortega?, Move Kestrel Labs, Cancel your RSVP?, Link to Tomás’s profile?.
  • Destructive confirmations: Delete Ben Carter for good? (type DELETE), Suspend Leah Thompson? (reason required), Cancel Toronto Builders Night?, Remove Volunteer from Ruth Alvarez?, Delete this photo?.

The bell panel is the only non-modal overlay. Under 640px, a dialog becomes a bottom sheet. The only drawer is the Main menu (tab bar More); there are no other popovers or tooltips.

Stacking

  • Only one overlay at a time. A dialog never opens another dialog. Opening a dialog closes the bell panel.
  • Toasts (--z-toast) sit above dialogs (--z-modal) and the backdrop (--z-overlay), so "Contact archived · Undo" is still visible as the dialog closes.

Structure

A dialog has a backdrop and a panel. The panel has a header (icon, title, description, Close), a body and a footer. In the footer, Cancel comes first and the main action comes last. The examples below are shown in place with .dialog--static.

Delete a contact: type DELETE

Delete Ben Carter for good?

This removes the contact and all 4 of your notes. It can’t be undone.

dialogs/delete-contact/default. Delete permanently checks the typed text when pressed. The button is never disabled, so the person always learns why nothing happened.

dialogs/delete-contact/invalid, busy and failed.
StateWhat changes
DefaultFocus is on the first field. In a confirmation with no fields, focus is on Cancel.
InvalidThe error appears under the field and focus moves to the field. The dialog stays open.
BusyThe pressed button shows the spinner and keeps its type: a button that is type="button" in the default state stays type="button" while busy. Cancel and Close are disabled. Esc does nothing.
FailedA danger alert at the top of the body names what was not saved ("Invite not sent", "Contact not deleted") and says that nothing changed. What the person typed is kept. Focus moves to the alert.
SuccessThe dialog closes, focus returns to the button that opened it, and a toast confirms: "Contact archived · Undo", "Invite sent".

Responsive behaviour

  • From 640px, the dialog is centred, up to 32rem wide, and at most 90% of the viewport tall. The body scrolls, and the header and footer stay in view.
  • Under 640px, the dialog becomes a bottom sheet that fills the width, with the footer buttons stacked full width. The main action sits closest to the thumb.
  • The bell panel becomes a link to the Notifications page on phones.

Accessibility

Role and pattern

The dialog follows the WAI-ARIA APG modal dialog pattern. It uses role="dialog" and aria-modal="true", is labelled by its title and described by its description. CDK Dialog traps focus inside, makes the page behind it inert, and restores focus when it closes. Don't build a modal by hand.

Keyboard

KeyAction
Tab / Shift+TabMoves through the controls and wraps inside the dialog.
EscCloses the dialog, the same as Cancel. It does nothing while the dialog is busy.
Enter in a fieldSubmits the dialog form.

A destructive dialog (its main button is danger) tints its icon with .dialog__icon--danger; dialogs that can be undone keep the neutral icon. In the app this is ft-dialog tone="danger".

Focus

In a destructive dialog, focus starts on the DELETE field or the reason field, never on the danger button. A dialog with no fields puts focus on Cancel. The mocks mark that start with autofocus; the app marks it with cdkFocusInitial. Clicking the backdrop does nothing in destructive dialogs, so a stray click can't throw away a typed reason.

Content

  • The title is a question that names the thing: "Delete Ben Carter for good?", "Suspend Leah Thompson?", "Archive Tomás Ortega?".
  • The description says what happens and whether it can be undone: "It can’t be undone." or "You can restore him whenever you like." Mention the audit log when the action is recorded there.
  • The main button repeats the verb: Delete permanently, Suspend, Archive, Send invite, Move to Confirmed. Never "OK" or "Yes".
  • The safe button is always "Cancel". Where "Cancel" is also the action (Cancel event, Cancel RSVP), the safe button says "Keep event" or "Keep my RSVP".
  • Failures say that nothing changed: "Nothing was changed — try again."

Accessibility

WCAG 2.2 AA in both themes, for every member and every anonymous visitor: 44px controls, one visible focus ring, a keyboard path for every drag, plain-language errors and no motion for those who opt out.

Overview

FaithTech Community is used by adults with very different set-ups: Staff reviewing on a laptop, City Leads like Grace Okonkwo updating the partner pipeline on a phone between meetings, volunteers with a screen reader, and anonymous visitors who arrive on a shared public event page and RSVP as guests. The system commits to WCAG 2.2 level AA in both themes. This page lists the commitments, the keyboard path for each interactive screen, the tokens that enforce them and how each component page proves them.

Perceivable

CommitmentWCAGRule in FaithTech Community
Text contrast1.4.3Body, label and secondary text at 4.5:1 or more on every surface it sits on, in both themes; large text at 3:1. Pairs live in tokens/contrast-pairs.json, including muted captions on Kanban cards and the badge counts.
Non-text contrast1.4.11Field edges, the focus ring, meaningful icons, the selected estimate card in Planning Poker and the unread dot in the bell panel at 3:1. Decorative dividers are exempt.
Use of colour1.4.1Status is colour + icon + words: “This event was cancelled”, “Read-only for Staff”, “Unread” in the notice meta; links are underlined; optional fields say “(optional)”.
Images1.1.1Profile photos require alt text before they save (“Describe what’s in the photo for people using screen readers.”); avatars with initials are aria-hidden beside the visible name; event photos have alt describing the scene.
Reflow and zoom1.4.4, 1.4.10Every screen works at 320px and 400% zoom: the Kanban columns stack, tables scroll inside .table-wrap, the sidebar becomes the tab bar.
Text spacing1.4.12No fixed heights on text containers; notice and card text wraps.

Operable

CommitmentWCAGRule in FaithTech Community
Keyboard2.1.1, 2.1.2Everything works with Tab, Shift+Tab, Enter, Space and Escape, with arrows inside menus, tabs and radio groups. No traps; dialogs and the bell panel release on Escape.
Dragging alternative2.5.7Every drag has a single-pointer, keyboard path: a partner card’s Move button opens the Move dialog (stage radio group plus an optional note); work-item cards on the team board do the same.
Focus visible2.4.7One ring everywhere: --focus-ring-width of --color-focus-ring with --focus-ring-offset on :focus-visible, at least 3:1 against what it sits on.
Focus not obscured2.4.11The sticky top bar, the tab bar, the bell panel and toasts never cover focus; scroll-padding-top matches the top bar.
Focus order2.4.3DOM order is visual order; no positive tabindex; Kanban columns read Lead, In funnel, Confirmed.
Bypass blocks2.4.1A skip link to #main on every page, then landmarks: banner, navigation, main.
Timing2.2.1No timeouts on forms. Toasts with an action (Undo, Retry) pause on hover and focus, and the action is also reachable elsewhere (archived contacts, the RSVP button).
Target size2.5.8At least 24px everywhere (--target-min); 44px for buttons, fields and icon buttons (--target-comfortable).

Understandable

CommitmentWCAGRule in FaithTech Community
Labels3.3.2A visible label on every control; placeholders are never labels; optional fields say so in the label (“Email (optional)”).
Errors3.3.1, 3.3.3Field errors name the fix (“Enter an email like name@example.org.”) with aria-invalid="true" and aria-describedby; a summary (“Fix 2 things to save”) links to each field and receives focus on submit.
Error prevention3.3.4Destructive actions are confirmed in a dialog that names the object (“Delete Ben Carter for good?”); typed confirmation where it cannot be undone (“Type DELETE in capitals to confirm.”); archiving and restoring a contact can be undone from its toast.
Redundant entry3.3.7A guest RSVP on a public event asks only for name and email once; an invite pre-fills the email on sign-up.
Accessible authentication3.3.8Sign-in allows paste and password managers (autocomplete set); no cognitive tests; password reset by email link.
Consistent help3.2.6Forbidden pages name who can help in the same place (“Ask Grace Okonkwo, your City Lead…”).
Language3.1.1lang="en" on every page; English only in v1.

Robust

CommitmentWCAGRule in FaithTech Community
Name, role, value4.1.2Native elements first (button, a, input, fieldset, table); ARIA only to fill gaps, following the WAI-ARIA Authoring Practices pattern named on each component page. Estimate cards use aria-pressed.
Status messages4.1.3Success toasts in role="status" (“Invite sent”); failures in role="alert" (“Your RSVP wasn’t saved”); loading regions carry aria-busy="true" and a label (“Loading contacts”).
Valid HTML—No duplicate ids; no interactive element inside another (the Kanban card title link and its Move button are siblings).

Keyboard by screen

ScreenKeys and behaviour
Partner KanbanTab moves through each card’s title link then its Move button, column by column. Move opens the Move dialog: arrows choose Lead, In funnel or Confirmed, Tab reaches the note, Enter on “Move to Confirmed” saves and focus returns to the card in its new column. Drag and drop is an extra, never the only way.
DialogsFocus moves into the dialog on open (CDK focus trap); Tab cycles inside it; Escape and Cancel close it; focus returns to the button that opened it. Destructive dialogs start focus on the safe choice.
Bell panelThe bell button is named “Notifications, 3 unread” and has aria-expanded. Enter opens the panel; Tab reaches “Mark all read”, each notice’s link and “See all”; Escape closes it and returns focus to the bell.
Tables (People, Audit log, Admin users, Backlog)Header cells use scope="col"; each row’s actions are buttons named with the person (“Reinstate Victor Kane”); if a header ever sorts, it becomes a button with aria-sort (no mock sorts yet).
Forms (Contact, Event, Sign up, Public RSVP)Tab order follows the visual order; Enter submits; on submit with errors focus moves to the summary; the busy submit button keeps focus and announces with aria-busy (“Add partner…”).
Planning PokerEstimate cards are toggle buttons in a row; Tab reaches them, Space or Enter picks one (aria-pressed="true"); the facilitator’s Reveal button is next in order.

Targets and controls

Move 3
Control heights sm 36px, md 44px, lg 52px. The count badge on the bell is the smallest target-sized element at 24px.

Focus

The ring is an outline, not a shadow, so it survives forced-colours mode (where it becomes Highlight). Text fields draw it with no offset and also colour their border, so the ring hugs the field. Menu items show focus as the hover background instead, because the menu panel is already a clear container.

Component contract

Every component page’s Accessibility section answers the same seven questions:

  1. Role and pattern: the native element or WAI-ARIA Authoring Practices pattern used.
  2. Keyboard: a table of keys and what they do, including the non-drag path.
  3. Focus: where focus starts, where it goes on close, how the ring looks.
  4. Labelling: what is labelled, how, and what is announced.
  5. Contrast: the token pairs involved, measured live in both themes.
  6. Motion: what moves and what happens under reduced motion.
  7. Touch: target sizes and the alternative to any hover or drag.

Testing

  • scripts/check_contrast.py for every pair in both themes.
  • scripts/check_design_system.py for labels, names, alt text, landmarks, headings and links.
  • Tab through every example on a component page; nothing is skipped, nothing traps.
  • A screen reader on one dialog (Move Kestrel Labs), one form (New contact), one table (Audit log), the bell panel and the public event page signed out.
  • Move a partner from Lead to Confirmed with the keyboard only.
  • Zoom to 200% and 400%; emulate prefers-reduced-motion, prefers-contrast: more and forced-colors: active in Chrome DevTools.
  • Playwright acceptance tests run axe on every screen and assert accessible names and roles through page objects, in Chromium.
